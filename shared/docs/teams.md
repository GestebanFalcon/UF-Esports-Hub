# Team data and API conventions (PBI 7 / #15)

This is the persistence and contract baseline for [#18 team routes](https://github.com/GestebanFalcon/UF-Esports-Hub/issues/18), PBI 8 creation, and PBI 9 viewing. Contracts live in `shared/src/team.ts` and are exported from `@uf-esports-hub/shared`. Team endpoints are implemented separately in #18.

## Persistence and rules

| Table / field | Storage | Rule |
| --- | --- | --- |
| `teams.id` | UUID primary key, generated by PostgreSQL | Server assigned |
| `teams.name` | varchar(100), required | Nonblank; API trims surrounding whitespace |
| `teams.game` | varchar(80), required | Nonblank free text; API trims surrounding whitespace |
| `teams.description` | varchar(500), required, default `''` | Empty string clears it; API trims surrounding whitespace; `null` is invalid |
| `teams.manager_id` | Required FK to `users.id` | Ownership, independent of global role |
| `teams.created_at`, `updated_at` | Required timestamptz, default now | Internal metadata; Drizzle updates refresh `updated_at`; SQL writers must refresh it explicitly |
| `team_memberships.team_id` | Required FK to `teams.id` | Part of composite primary key |
| `team_memberships.player_id` | Required FK to `users.id` | Other part of composite primary key |
| `team_memberships.joined_at` | Required timestamptz, default now | Internal metadata |

`teams_game_name_unique` makes `(lower(btrim(game)), lower(btrim(name)))` unique across all owners. For example, `Gators / Rocket League` conflicts with ` gators / rocket league ` but can coexist with `Gators / Valorant`. This follows PostgreSQL `lower` and `btrim` semantics (space trimming); it does not merge game aliases or internal whitespace. The API trims JavaScript whitespace before storage. Database checks also reject empty or space-only names and games. Field lengths are enforced by PostgreSQL as well as Zod.

One user can own multiple teams and join multiple rosters, including teams for the same game. A `(team_id, player_id)` pair can occur only once. Ownership does not automatically add the owner to a roster. Owners may also be roster members. Membership means a user participates on a team; it does not grant or depend on a global `player`, `manager`, or `admin` role. There are no roster sizes, positions, invitations, or historical memberships in this model. Removing a membership deletes the row; a later rejoin gets a new `joined_at`.

Deleting a team cascades to its memberships and preserves users/profiles. Teams referenced by matches must first follow the [match deletion rules](matches.md#fields-and-persistence). Deleting a roster user cascades to their memberships. Deleting an owner is **restricted** while any team references them, even if they also have memberships. An explicit team deletion or ownership transfer must precede owner deletion; those operations require their own authorization and API contracts. There is no orphaned or automatically reassigned team. Changing a global role does not change ownership or membership. Foreign keys remain stable UUID links; there is no mutable username relationship. Indexes support owner lookups and player-to-team lookups; the membership primary key supports roster lookups.

## Shared contracts and visibility

| Export | Shape / purpose |
| --- | --- |
| `teamCreateSchema` / `TeamCreate` | Required `name`, `game`, `description` strings; strict body |
| `teamUpdateSchema` / `TeamUpdate` | At least one defined editable field; strict partial body |
| `teamSchema` / `Team` | Public `id`, `name`, `game`, `description`, `managerId` |
| `teamResponseSchema` / `TeamResponse` | `id`, `name`, `game`, `description`, `managerId` |
| `teamListSchema` / `TeamList` | `{ teams: TeamResponse[] }` |
| `teamRecordSchema` / `TeamRecord` | Team response fields plus `createdAt`, `updatedAt` as `Date` |
| `teamMembershipRecordSchema` / `TeamMembershipRecord` | `teamId`, `playerId`, `joinedAt` as `Date` |
| `teamRosterMemberSchema` / `TeamRosterMember` | Only `playerId` and profile `displayName` (1–40 characters) |
| `teamRosterSchema` / `TeamRoster` | `{ members: TeamRosterMember[] }` |
| `teamParamsSchema` / `TeamParams` | `{ id: UUID }` route parameter validation |
| `teamErrorSchema` / `TeamError` | `{ message: string, fieldErrors?: Record<string, string[]> }` |
| `teamFieldLimits` | Shared 100/80/500 character limits |

Create/update reject unknown and protected fields, including `managerId`, `id`, roles, membership arrays, and timestamps. An empty description is required for a create form without a description; omitting it is a validation error even though direct database inserts have a default. PATCH omission preserves a field; `description: ''` clears it. Neither operation accepts ownership transfers or roster changes.

Use `toTeam(databaseRow)` before returning data. Like `toUser` and `toProfile`, it selects the public fields explicitly. `teamResponseSchema` is an alias for `teamSchema`. Read schemas validate text without trimming or changing saved values; only create/update schemas trim input. Public team data contains the owner's UUID so clients can identify ownership, but no account email, password hash, global role, nested account, or database timestamps. Team endpoints require authentication. Success response schemas strip unknown fields, whereas write schemas reject them.

Roster reads join `team_memberships.player_id` to `player_profiles.user_id` and use `toTeamRosterMember(profileRow)`; the user UUID supports stable roster identity and the profile supplies the public display name. No username, email, bio, favorite game, role, join date, or account metadata is returned. Apply the existing profile backfill before reading rosters; account registration already creates profiles transactionally. A missing profile must be repaired or surfaced as an internal data error, rather than silently dropping the member. The membership FK targets the user so profile edits do not alter membership.

## Route conventions for #18

Preserve the existing PBI 10 branch's export names and response shapes. Mount its future router at `/api/teams` after verified authentication and role integration. IDs are UUIDs, validated using `teamParamsSchema`; path builders escape supplied IDs but do not replace validation.

| Method | Path / shared builder | Success | Access |
| --- | --- | --- | --- |
| GET | `/api/teams` / `teamPaths.list` | 200 `TeamList` | Any authenticated user |
| GET | `/api/teams/:id` / `teamPaths.detail(id)` | 200 `TeamResponse` | Any authenticated user |
| POST | `/api/teams` / `teamPaths.list` | 201 `TeamResponse`; `Location: teamPaths.detail(id)` | Current global role must be `manager`; owner is verified actor |
| PATCH | `/api/teams/:id` / `teamPaths.detail(id)` | 200 `TeamResponse` | Current global role must be `manager` and actor must own the team |
| GET | `/api/teams/:id/roster` / `teamPaths.roster(id)` | 200 `TeamRoster` | Reserved roster read extension; any authenticated user |

The initial #18 scope is list/detail/create/update. The roster read has a defined contract for a subsequent integration; it is not an implemented route. No roster mutations, self-join, DELETE, owner transfer, admin override, filters, or pagination are part of these contracts. Empty collections return `{ teams: [] }` or `{ members: [] }`; a nonexistent team's roster returns 404. Do not silently add a roster to team list/detail responses.

For writes, load the current role from trusted server data, never body fields or client-supplied headers. Obtain `managerId` from the verified JWT subject and confirm the account still exists. Apply ownership atomically with `UPDATE teams ... WHERE id = :teamId AND manager_id = :verifiedUserId`. Return the same 404 for nonexistent and non-owned teams. A global manager role alone does not permit modifying someone else's team, and an ownership FK alone does not authorize a user with a different current role. Admin writes remain denied in this MVP, matching the PBI 10 branch. Role integration is a separate dependency; this migration does not add or grant global roles.

All errors use `TeamError`: 400 invalid UUID/body (optional `fieldErrors`), 401 missing/invalid session or deleted actor, 403 forbidden role, 404 missing/not-owned resource, 409 conflicting data, 500 unexpected storage failure. Map unique violations on `teams_game_name_unique` to a generic 409, including PATCH conflicts. Never return raw database errors, queries, or constraint details to clients. Resource-level validation and role checks belong in the route/store layer; Zod and foreign keys do not authenticate callers.

## Migration, fixtures, and verification

`backend/drizzle/0003_team_schemas.sql` follows the existing users/profile migrations and adds empty team tables. It does not rewrite accounts/profiles or grant roles. Its Drizzle snapshot and journal are checked in.

```sh
cd backend
bun install
bun run db:migrate
# Optional fixtures: export DATABASE_URL in this shell first; psql does not load .env.
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f seeds/teams.sql
```

The development-only SQL seed creates two disabled-login accounts with profiles, two teams with the same name in different games, and the same player on both rosters. Re-running it preserves existing rows/edits using fixed UUIDs and conflict handling. It grants no global manager role and cannot enable API writes. Use registered accounts and the role feature's development grant workflow when testing authenticated writes; do not copy disabled seed hashes to real accounts.

Run `bun run test` in `shared` and `backend`; run typechecks/builds in all three packages. Backend tests use test-only [PGlite](https://pglite.dev/docs/about), a disposable in-memory PostgreSQL build, and the Drizzle migrator. They apply the complete migration chain twice, exercise repeatable fixtures, upgrade an existing account/profile database, verify foreign keys, case/space-insensitive name conflicts, field constraints, composite membership uniqueness, Drizzle timestamps, and restrict/cascade deletion. They do not use `DATABASE_URL`, connect to the configured development database, or test the future HTTP routes. Shared tests cover protected fields, limits, validation, safe serialization, paths, and roster privacy.
